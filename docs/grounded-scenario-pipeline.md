# 대화와 상세 생성을 분리한 시나리오 흐름

## 대화 단계

`/internal/ai/discovery/next`는 `discovery_brief` 모델 호출 한 번만 수행한다.
모델은 새로 확인한 사실과 다음 질문 목적만 반환한다. 서버가 누적 상태로 준비 여부와 질문 문장을 결정한다. 활동 이름만으로 준비 완료하지 않는다.
이 단계는 사실 그래프·사기 유형·전체 계획을 만들거나 별도 의미 검증 모델을 호출하지 않는다.

마스킹된 사용자 발언을 `facts.discoveryEvidence`에 보관한다. 질문은 사용자 사실에 포함하지 않는다.
최대 20개 발언, 직렬화 9000자 이내의 최근 기록을 유지한다. 컨텍스트가 잘린 요청에서도 저장된 근거와 현재 입력을 합친다.
새 답변은 이전 계획/준비 상태를 그대로 재사용하지 않는다. 준비 판정의 quote는 실제 사용자 발언과 대조한다.
`canGenerateScenario=true`는 상세 생성을 시도할 맥락이 있다는 뜻이며, 상세 검증 통과를 보장하지 않는다.

## 시나리오 만들기 단계

사용자가 생성을 요청하면 다음 순서로 처리한다.

1. 저장된 사용자 근거로 공통 사실 그래프와 서로 다른 짧은 접근 후보 두 개를 한 번에 작성한다 (`candidate_plan`).
2. 인용 출처, 행동 주체, 사건 ID와 개인화 근거를 코드로 검사한다.
3. 별도 모델 호출로 두 후보의 사실·주체 보존, 수신 이유, 맥락 충분성, 실제/가상 구분과 접근 차이를 비교한다 (`candidate_compare`). 승인된 후보 중 사실 근거·개연성·독창성 순으로 선택한다.
4. 통과한 계획으로 본문을 생성한다.
5. 본문의 구조·안전성 및 의미를 다시 검사한다.
6. 승인한 본문에 자유 세부 유형명·태그·기존 API 호환용 대표 코드를 붙인다. 참고 사례는 실제 겹치는 수법을 확인할 수 있을 때만 연결하고, 그 결과로 본문을 고치지 않는다.

빠른 대화 판단이 잘못됐어도 상세 검증을 생략하지 않는다. 상황이 부족하면 422로 추가 설명을 요청하며 생성기는 호출하지 않는다.
생성의 제한된 재시도는 유지하고, 계속 실패하면 명시적 오류를 반환한다. 무관한 기본 시나리오로 성공을 가장하지 않는다.
이전의 그래프/계획 기반 상태와 facts-only 요청 경로도 유지한다. 기존 상세 context-turn API의 검증 흐름은 변경하지 않았다.

## 충분한 맥락의 기준

활동·품목·장소 이름만으로 일반적인 이야기를 떠올릴 수 있다는 것은 충분하지 않다.
관계자의 실제 역할/행동, 진행 방식, 구체적인 상호작용 같은 근거 때문에 접근 인물·구실·대응이 달라질 수 있어야 한다.
계획의 `personalizationBasis`에 사건과 인용 ID를 연결하고 별도 검증자가 의미를 검사한다.
관련 맥락 하나로 충분할 수 있다. 질문 횟수·도메인별 필수 항목·실명·특별한 사건을 강제하지 않는다.
가상 사기 연락이 실제로 왔어야 하는 것도 아니다.

## 설정과 시간

- `DISCOVERY_REASONING_EFFORT`: 대화 판단에만 적용. 기본은 공급자 기본 설정이며 현재 로컬은 지원 여부를 확인한 `none`.
- `DISCOVERY_TIMEOUT_SECONDS`: 대화 호출 대기 설정, 기본 5초. 2초를 강제해 정상 응답을 오류로 바꾸지는 않는다.
- `PIPELINE_REASONING_EFFORT`: 상세 계획·의미 검증·생성에 적용. 현재 로컬은 `low`.
- 대화의 OpenAI 연결은 60초 keep-alive로 재사용한다. 요청별 timeout과 재시도 없음 설정을 유지한다.
- BE·FE API의 외부 success/data 형식과 endpoint는 유지했다. BE/FE 코드는 수정하지 않았다.

2026-11-19 실제 평가: 같은 모델, 대화 4회 2.536 / 1.476 / 1.263 / 1.335초.
평균 1.652초, 2초 이내 3/4회다. 첫 요청을 포함해 항상 2초를 보장하는 결과는 아니다.
별도 시나리오 만들기는 1회 48.447초였다. 대화 시간 단축은 이 작업을 버튼 클릭 시점으로 옮긴 결과도 포함한다.
FE/Spring 통신 전체 시간이 아닌 AI 서비스 함수의 시간이다. 표본이 작으며 일반적인 성공률·지연 보장은 아니다.
평가 프로토콜은 `deferred-discovery-v1`, 결과는 Git 제외된 `evaluation-results/20261119T082013396256Z/`에 있다.
검증 모델도 같은 계열 모델이므로 의미 오류가 없다고 보장하지 않는다. 실제 사례의 정답과 사람의 검토를 함께 사용한다.

## 생성 오류 재검증 (2026-11-20)

생성 요청에도 추가 질문 단계의 지시가 섞여 selectedPlan=null을 반환하고 다시 호출하는 문제가 있었다.
생성 작성자용 `generation_plan.md`와 대화용 `intake_plan.md`를 분리했고, 두 단계의 실제 사실 추출 규칙은 `context_facts.md`로 공유한다.
또한 장면의 goal/tactic은 사기범의 유도 행동, expectedActions는 사용자의 안전한 대응이라는 구분을 스키마와 생성 지시문에 명시했다.
검증자의 사실·주체 보존 검사와 독립적인 거절은 유지했다.

승인받은 실패 입력을 같은 조건으로 재실행했다. 수정 전 성공 실행은 계획 형식과 본문 의미 오류 재시도로 71.678초가 걸려 Spring의 60초 제한을 넘었다.
수정 후 실제 실행 1회는 계획 17.917초, 계획 검증 3.168초, 본문 11.063초, 본문 검증 4.872초, 총 37.040초로 재시도 없이 완료됐다.
결과는 Git 제외된 `evaluation-results/generation-check-20261120T001751Z/`에 보관했다. 대화 원문은 소스·테스트 데이터에 추가하지 않았다.
단일 사례의 AI 서비스 검증이며 모든 입력의 성공이나 브라우저 전체 시간을 보장하지 않는다. BE/FE 코드는 이번에 변경하지 않았다.

## 유형을 생성 이후로 분리 (2026-11-20)

계획과 본문은 고정 유형·위험 대분류로 결정하지 않는다. 현재 계획의 referenceUses에는 생성 전 검색에서 실제 참고한 수법 ID를 기록하며, 본문에는 사례 ID를 쓰지 않는다. 검색된 사실 수법만 선택적으로 전달한다.
계획은 사용자 사실을 바탕으로 인물·접근 경로·구실·요구 행동을 구성한다. 사실·주체 보존과 기존 안전 검사는 유지한다.
완성된 본문이 의미 검증을 통과한 다음 `scenario_classify`가 분류 메타데이터만 반환한다.
분류 응답은 본문 필드를 포함할 수 없고, 형식 오류는 분류만 제한적으로 재시도한다. 분류 오류를 이유로 작성을 다시 호출하지 않는다.

- `fraudSubtype`: 고정 9종 선택지 대신 자유로운 구체적 수법 이름.
- `tags`: 사칭 대상·구실·요구 행동 등 자유 태그.
- `fraudTypeCode`와 `riskType`: 기존 FE/BE 연동을 위한 대표 코드와 대분류. 정확히 대응되지 않으면 `classificationFit=APPROXIMATE`.
- `classificationReason`: 완성된 이야기에서 도출한 분류 이유.
- `basedOnCases`: 실제 참고할 기법이 겹치는 자료만 연결. DB의 요청 행동/기법을 정확히 참조하는지 코드 검사.
- `referenceStatus`: 관련 자료가 없으면 NOT_MATCHED와 빈 목록을 반환하며, 무관한 출처를 강제로 붙이지 않는다.

기존 저장 계획의 유형/사례 ID는 읽을 때 생성 경로에서 분리한다. 기존 시나리오/역할극 데이터와 대표 코드 7종은 유지한다.
채널·요구 행동·모의 화면의 지원 범위는 이번 변경에서 확대하지 않았다. 반복 질문을 막는 대화 상태 관리는 별도 작업이다.

실제 검증 1회는 계획→계획 검증→본문→본문 검증→분류 순으로 34.979초에 성공했다.
동일 본문의 호환 코드 설명을 보완한 뒤 분류만 별도로 4.711초에 재검증했다. 본문은 변경하지 않았다.
결과는 Git 제외된 `evaluation-results/narrative-first-20261120T004340Z/`에 있다.
단일 사례 성공은 다양성·맥락 유지 품질의 개선을 통계적으로 증명하지 않는다. 평가 프로토콜은 narrative-first-v1이며 추가 비교 평가가 필요하다.

## 대화 상태와 질문 목적 관리 (2026-11-20)

- `knownTopics`에 활동, 장소, 서비스, 참여자, 목적, 접근 경로/기기, 상호작용, 거래 방식, 역할의 확인 상태와 사용자 인용을 저장한다.
- `questionHistory`에 무엇을 물었는지와 질문 시점(turn)을 보관한다. 확인·거절·해당 없음으로 처리한 항목 및 이미 질문한 목적은 다시 선택할 수 없다.
- 모델이 자유로운 질문 문장을 쓰지 않는다. 아직 필요한 질문 목적을 선택하면 서버가 그 목적에 맞는 공통 질문을 표시한다. 운동/음식/서비스마다 개별 조건을 두지 않는다.
- 실제 활동과 그에 관련된 주변 맥락 하나가 확인되면 서버가 준비를 마친다. 관련 항목을 모두 채우거나 정해진 답변 횟수를 채우도록 강제하지 않는다.
- 장소만 알고 실제 활동이 없으면 활동을 먼저 묻는다. 활동을 기억하지 못하거나 맥락을 더 말하지 못하고 남은 질문 목적도 없으면 계속 질문하지 않고 멈춘다.
- 짧은 답변의 의미(topic)도 원문 turn/quote와 함께 생성 단계로 전달한다. 메타데이터 자체는 새 사실의 근거가 아니며 인용은 원문과 대조한다.
- 기존 대화에 상태가 없으면 보존된 발언에서 상태를 복원할 수 있다. 대화 기록을 줄일 때 활성 사실의 출처를 우선 보존한다.

새 운동/시청 대화는 외부 API에 보내지 않았다. 관련 상태 전이는 가상 회귀 사례로 검증했다.
기존에 OpenAI 전송을 승인받은 입력으로 실제 확인한 결과, 첫 답변에서 활동을 물었고 두 번째 답변 뒤 준비를 마쳤다. 대화는 각각 2.359초, 1.212초였다.
결과: Git 제외된 `evaluation-results/stateful-discovery-20261120T013449Z/`. 단일 실행이며 항상 2초 이내를 보장하지 않는다.
평가 프로토콜은 stateful-discovery-v1이다. 개인정보·사실 보존과 생성 후 분류 단계는 유지했다.

## 접근 후보 비교와 반복 패턴 검토 (2026-11-20)

개인정보 요구를 모든 시나리오의 필수 장면으로 두지 않는다. 링크 클릭·송금·앱 설치·개인정보 제공 중 상황에 맞는 위험 행동을 선택한다. 개인정보를 요구하는 장면에만 requestedInfo를 필수로 검사한다.

후보는 인물 이름만 바꾸지 않고 접근 구실·요구 행동·전개 방식에 차이를 둔다. 생성 전에 고정 사기 유형을 주입하지 않는다. 현재는 관련 사실 수법을 검색해 선택적으로 참고하며, 적합하지 않으면 사용하지 않는다. 후보 비교에서 근거 없는 후보는 독창성 점수가 높아도 선택하지 않는다. 의미상 같은 후보는 한 번만 다시 작성하며, 승인 후보가 없으면 오류를 반환한다.

후보 비교와 본문 검토에는 contextDrivesPlot(사용자 맥락이 줄거리를 바꾸는지), nonGenericProgression(이름만 끼운 일반 패턴인지)을 추가했다. 링크나 정보 요구 자체를 금지하지는 않는다. 과거 모든 훈련과 비교하는 중복 방지 기능은 아니며, 모델 검토가 오류를 완전히 방지하지도 않는다.

외부 호출은 기본 5회(candidate_plan → candidate_compare → scenario_generate → semantic_review → scenario_classify)이며 형식 복구·의미 재시도 시 증가한다. 후보 점수는 모델 판단값으로 실제 품질 정확도를 뜻하지 않는다.

개인정보 없는 동일한 가상 예약 상황을 두 번 실제 호출해 모두 완료했다. 첫 실행은 송금 중심으로 39.626초, 두 번째는 링크 클릭 중심으로 52.422초였다. 두 번째는 본문 모순 검출로 한 번 재생성했다. 두 결과 모두 개인정보 요구 장면이 없었다. 두 표본만으로 다양성 향상이나 지연 목표 충족을 입증하지는 않는다. 상세 결과는 Git 제외된 evaluation-results/candidate-diversity-20261120T030647Z/trace.json에 있다.

## 질문 목록 순회와 호칭 강제 문제 수정 (2026-11-20)

질문은 모델이 선택한 nextTopic이 실제 requiredTopics의 미해결 항목일 때만 허용한다. 선택에 실패했을 때 남은 항목의 첫 질문을 꺼내던 동작은 제거했다. 이미 답한 주제·거절한 주제·두 번 질문한 불완전 항목은 다시 묻지 않는다.

PERSON_NAME은 실명 전용 항목이 아니라 사용자가 상대를 부르는 이름·별명·관계 호칭이다. 평소 부르는 가족 호칭이 확인되면 그 실제 인용과 호칭을 저장해 생성에도 보존한다. 모르는 서비스명·계정 관리자·결제 정보를 모든 상황의 필수 조건으로 두지 않는다.
