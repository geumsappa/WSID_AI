# 피해 대응 OCR 구현 보고서

작성일: 2026-11-19  
작업 브랜치: `feature/ocr-paddle-v2` (최신 `develop` `ad1f73c` 기준)

## 구현 내용

`POST /internal/ai/ocr/extract`는 기존 내부 키 인증과 multipart `images`를 유지한다. PNG/JPEG 최대 3장, 장당 5MB, 이미지당 1,600만 픽셀 제한과 텍스트가 없는 경우의 `OCR_FAILED`도 유지한다.

1. 기본 엔진을 PaddleOCR PP-OCRv5 한국어 인식 모델로 전환했다. 프로세스 시작 시 CPU 모델을 한 번 로드하며 OCR 결과 상자를 위에서 아래, 같은 줄에서는 왼쪽에서 오른쪽으로 정렬한다. 좌우만으로 대화자를 판단할 수 없어 말풍선 방향 표시는 넣지 않았다.
2. `OCR_ENGINE=tesseract`로 기존 실행 파일과 `OCR_LANGUAGES`를 사용하는 경로로 되돌릴 수 있다. `requirements.txt`에 PaddleOCR과 PaddlePaddle을 추가했다. 최초 모델 다운로드와 프로세스마다 모델을 로드하는 데 드는 시간·메모리를 배포 환경에서 확인해야 한다.
3. 민감정보가 감지돼도 인식 원문을 버리지 않는다. LLM 분류에 앞서 기존 민감정보 정규식에 더해 URL과 전화번호, 문맥상 인증번호 등을 가린다. 사진 종류와 300자 이내 요약을 검증한다. 허용되지 않은 유형은 `OTHER`, 링크·연락처·민감정보로 탐지된 요약은 `null`로 처리한다.
4. OCR은 최대 15초(동시 요청 대기 포함), 분류는 최대 10초(`OCR_CLASSIFY_TIMEOUT_SECONDS`)를 기다린다. 분류 오류·시간 초과·분류 작업 중에는 OCR 원문을 그대로 반환하고 유형은 `OTHER`, 요약은 `null`로 대체한다. Paddle 모델과 분류기는 각각 프로세스당 작업 한 개만 실행하며, 사용 중이면 OCR은 최대 5초(`OCR_QUEUE_WAIT_SECONDS`), 분류는 1초 기다린 뒤 처리한다. 타임아웃은 이미 시작된 작업을 강제로 중단하지 않으므로 작업이 끝날 때까지 슬롯을 점유한다.
5. Paddle 로드에 실패해도(미설치·모델 다운로드 실패·잘못된 `OCR_ENGINE`) 서버는 기동하고 OCR 요청만 503을 반환한다.
6. 인식 텍스트는 1,000자(Spring `/extract` 상한)까지만 반환하고 넘으면 자른다. 분류에도 잘린 텍스트를 쓴다.

## Spring 응답 계약

```json
{
  "success": true,
  "data": {
    "recognizedText": "인식된 원문",
    "usable": true,
    "imageType": "MESSENGER_CHAT",
    "summary": "대화 내용을 요약합니다."
  }
}
```

`imageType`은 `SMS`, `MESSENGER_CHAT`, `TRANSFER_RECEIPT`, `WEB_PAGE`, `OTHER` 중 하나다. `summary`는 문자열 또는 null이다. 글자를 못 읽으면 기존처럼 422 `OCR_FAILED`이므로 성공 시 `usable`은 true다. OCR 원문은 가려지지 않은 값이며 민감정보를 포함할 수 있다. **Spring 응답 DTO, 직렬화, 사실 추출 경로와 로그·저장 정책을 함께 확인해야 한다.** Spring 저장소 변경 및 연동 검증은 이 작업에서 수행하지 않았다.

## 검증

- 기존 코드 포함 전체 Python 테스트 238개 통과: `OCR_ENGINE=tesseract`, `OCR_ENGINE=paddle`(Paddle 미설치 환경), `OCR_ENGINE=paddle`(Paddle 3.3.1 설치 환경) 세 가지 모두. OCR 함수와 분류 모델을 대역으로 바꾸어 민감정보가 들어간 원문 반환, 모델 입력 가림, 위험 요약 제거, 분류 실패·타임아웃, 좌표 정렬, 기존 인증 및 오류를 확인했다.
- 실제 PaddleOCR 모델을 초기화하고 합성 메신저 이미지로 내부 API를 호출했다. HTTP 200, 모델 초기화 약 1.75초(캐시 사용), 요청 약 1.55초였다. 이 요청은 이전 Gemini 경로의 가짜 모드로 수행했으므로 현재 OpenAI 분류 품질은 검증하지 않았다.
- Tesseract 전환 경로도 실제 실행 파일과 합성 문자 이미지로 호출해 HTTP 200을 확인했다.
- 실제 PaddleOCR 동시 2건: 둘 다 200 (1.3초, 2.7초). 두 번째 요청은 대기 후 처리됐다.
- 이전 Gemini 경로 측정(현재 OCR 분류 경로와 다름, 합성 택배 사칭 문자, 각 2회): `gemini-3.5-flash-lite` 1.3초·2.5초, `gemini-3.8-flash` 66.9초·90.1초. 둘 다 SMS로 분류했다. 이 수치는 OpenAI 분류의 응답 시간을 나타내지 않는다.
- 엔진 비교는 별도 작업 공간의 `docs/ocr-engine-comparison-2026-11-19.md` 참조. 소수 합성 이미지 실험으로 실사용 정확도를 확정할 수 없다.

## 운영 전 확인 사항

- 정규식 가림은 이름, 주소, 비정형 정보와 OCR 오류 등 모든 개인정보를 식별하지 못한다. 가려진 텍스트가 설정된 외부 LLM으로 전송되는 만큼 개인정보 처리 방침과 보호 조치를 먼저 확정해야 한다. 모델 출력을 금지 패턴으로 검사해도 안전성이 완전히 보장되지는 않는다.
- 대기 예산: OCR 15초 + 분류 대기 1초 + 분류 10초 = 최대 26초. Spring OCR 응답 제한(`ocrReadTimeout`, 기본 30초) 안이다. 이미지 검증·네트워크 시간은 제외한 값이라 배포 환경에서 실측 후 조정한다.
- OCR 분류는 공통 LLM 호출을 사용한다. OpenAI 사용 시 `LLM_PROVIDER=openai`, `LLM_API_KEY`, `LLM_MODEL`을 설정한다. `OCR_CLASSIFY_TIMEOUT_SECONDS`를 적용하고 한 번 호출한다. AI-06·07과 상담 assist도 OpenAI 경로를 사용한다.
- 분류 호출은 한 번 시도한다. 응답을 먼저 대체하더라도 실행 중인 호출은 백그라운드에서 완료될 수 있으며 비용이 발생할 수 있다. 호출이 끝나기 전까지 후속 분류는 대체 응답을 사용한다.
- 모델 실행 환경과 CPU 아키텍처, 네트워크가 제한된 배포 환경에서 모델 다운로드 및 캐시를 확인한다. 메신저·문자·이체 화면의 실제 사용 조건에 가까운 개인정보 없는 표본을 더 모아 정확도와 읽기 순서를 평가한다.

## OpenAI 전환 확인 (2026-11-19)

OCR 분류와 RAG 사실 추출, 답변 생성, 임베딩, 상담 assist를 OpenAI 설정으로 연결했다. 실제 OpenAI 키와 합성 입력으로 사실 추출, OCR 분류, 상담 모델 JSON 응답 및 1,536차원 임베딩을 확인했다. 근거 문단 45개 중 승인된 문단은 없어 서비스용 검색 인덱스는 만들지 않았다.

## OpenAI RAG 재시험

- 승인된 문단만으로 인덱스를 생성하려 했지만 현재 승인된 문단이 없어 생성되지 않았다.
- 미승인 근거 45개를 임시 디렉터리에만 인덱싱해 실제 OpenAI 검색을 시험했다. 사실 추출, 근거 5건 검색, 인용을 포함한 데모 질문 답변이 성공했다. 임시 인덱스는 시험 후 삭제됐다.
- 상담 assist PLAN은 기본 15초 제한에서 504 시간 초과가 발생했다. 30초로 임시 변경한 별도 시험에서 추가 질문은 5.16초에 성공했고, 근거 질문은 18.24초에 UNABLE_TO_ANSWER를 반환했다. 시간 제한 변경은 저장하지 않았다. 속도와 근거 적합성을 추가 개선·검증해야 한다.
- 모델 대역 테스트 242개가 통과했다. 실제 모델에 대한 위 결과는 소수의 합성 사례이며 품질을 일반화할 수 없다.
