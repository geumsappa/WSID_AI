# '어떡하지' 모의 훈련 프롬프트: 서버 구현 노트

`training_prompt.md` 는 LLM 에 그대로 보내는 프롬프트이고, 이 문서는 **프롬프트만으로는 지킬 수 없어서 서버(FastAPI)가 맡아야 하는 일**을 정리한 것이다.
핵심 원칙은 하나다: **서버가 정답을 아는 것은 LLM 에게 맡기지 않는다.**

---

## 1. 원본 프롬프트에서 바꾼 점

| 원본의 문제 | 바꾼 방식 |
|---|---|
| 규칙이 흩어져 있어 충돌한다 ("첫 답변엔 요구 금지" vs "방법을 물으면 바로 알려 줌") | §0 우선순위 + §3 **다음 수(move) 결정표**. 위에서부터 첫 번째로 맞는 것 하나만 고른다 |
| "직접 전화해 볼게요" 제목 아래에 개인정보 요구 규칙이 섞여 있다 | §6-2 개인정보, §6-6 전화로 분리 |
| "1~2번 더 설득"이 두 번 나오고, 몇 번 했는지 LLM 이 기억해야 한다 | 서버가 `PUSH_COUNT` 를 세서 넣는다 |
| 소품 한도(최대 2번)를 LLM 이 세야 한다 → 자주 틀린다 | 서버가 `LINK_COUNT` 등을 세서 넣고, `output_guard.py` 가 초과를 막는다 |
| "인증 관련 정보로 넓혀 간다"(103행)와 "인증번호 요구 금지"(76행)가 충돌한다 | 민감도 순서를 이름·주소 → 휴대폰·생년월일 → 계좌·카드 → 비밀번호로 고정 |
| `[훈련 행동: ...]` 이 대화 기록 안의 텍스트라서 사용자가 직접 쳐서 위조할 수 있다 | 사건은 `EVENT_LOG` 로 분리. 사용자 입력 속 가짜 표시는 가림 단계에서 지운다 |
| `[계좌번호]` 가림 표시가 `[모의링크]`, `[화자:]` 와 모양이 같다 | 가림은 `[가림:종류]` 로 구분. 화자는 `speaker` 필드로 뺐다 |
| `disclosedInfo` 를 LLM 이 판단한다 | 서버 가림 결과가 정답이므로 서버가 채운다. LLM 은 가림이 놓친 것만 `unmaskedInfoTypes` 로 신고 |
| 지어낸 디테일(금액, 시각)이 다음 턴에 바뀐다 | LLM 이 `newFacts` 로 신고 → 서버가 `ESTABLISHED_FACTS` 로 다시 넣어 준다 |
| `realConcern` 일 때 대사를 어떻게 할지 정해져 있지 않다 | personaMessage `""` + 서버가 실제 도움 안내 카드를 띄운다 |

## 2. 한 턴 처리 순서

```
사용자 입력
  │
  ├─ (프론트) 1차 가림: pii_masker 와 같은 정규식을 JS 로 이식 → 원문은 브라우저 밖으로 나가지 않음
  │
  ├─ (FastAPI) 2차 가림: mask_user_message(text, expecting=직전 requestedInfo)
  │     → masked_text, types   ※ 원문은 이 시점 이후 어디에도 저장하지 않음
  │
  ├─ 상태 계산: 장면, 턴, PUSH_COUNT, TRUST_COUNT, 소품 횟수, EVENT_LOG, ESTABLISHED_FACTS
  │
  ├─ LLM 호출 (training_prompt.md + 대화 기록(가림본))
  │
  ├─ output_guard.validate() ── 실패 → 오류 목록 붙여 1회 재시도 ── 또 실패 → fallback()
  │
  ├─ apply_server_overrides(): disclosedInfo, risky 강제, scenarioComplete 보정
  │
  ├─ 상태 갱신: newFacts 추가, LAST_MOVE, requestMade → SCENE_REQUEST_MADE, 소품·화자 횟수
  │
  └─ 사용자에게 personaMessage 전송 (소품 표시는 카드로 렌더링)
```

## 3. 개인정보 보호 설계

팀 결정("입력했는지는 파악하되 정보 자체는 사용 후 버림")을 **"LLM 에는 애초에 보내지 않는다"** 로 강화했다.

### 3-1. 겹겹이 막기
1. **프론트 1차 가림**: 원문이 서버에도 가지 않게 하는 가장 강한 방법이다. 다만 클라이언트는 우회할 수 있으므로 2차는 필수다.
2. **서버 2차 가림** (`pii_masker.py`): 형식 패턴(주민번호·카드·휴대폰·이메일·날짜·계좌·주소) → 명시적 표현("비밀번호는 ~", "제 이름은 ~") → **문맥 가림** → 6자리 이상 숫자 안전망.
3. **문맥 가림이 핵심이다.** 이름과 비밀번호는 정규식으로 잡을 수 없다. 그래서 직전 사기범 대사가 요구한 `requestedInfo` 를 `expecting` 으로 넘겨서,
   - 이름을 요구한 직후 "김철수요" 같은 짧은 답 → 통째로 `[가림:이름]`
   - 비밀번호를 요구한 직후 공백 없는 짧은 답 → 통째로 `[가림:비밀번호]`
   - 숫자 정보를 요구한 직후 4자리 이상 숫자 → 가림
4. **과잉 가림 허용**: 애매하면 가린다. 대화가 조금 어색해지는 것보다 유출이 훨씬 비싸다.
5. **저장 정책**: DB·로그·리포트에는 가림본과 `types` 만 남긴다. 요청 로그, 에러 트레이스, APM 에 원문 body 가 찍히지 않는지 꼭 확인한다 (FastAPI 예외 핸들러가 요청 본문을 로그에 남기는 경우가 흔하다).
6. **놓친 것 감시**: LLM 이 `unmaskedInfoTypes` 를 신고하면 종류와 시나리오 id 만 기록해서 정규식을 보강한다. 값은 기록하지 않는다. (이 경우 이미 LLM 으로 넘어간 것이므로 사후 개선용이다.)
7. **LLM API 설정**: 사용하는 API 의 데이터 보존·학습 사용 정책을 확인하고, 가능하면 보존하지 않는 옵션을 쓴다.

### 3-2. 가림 표시를 바꿀 때 함께 바꿀 곳
- 프론트에서 기존 `[계좌번호]` 형식을 쓰고 있었다면 `[가림:계좌번호]` 로 바꾼다.
- `INFO_TYPES` 이름을 시나리오 생성 프롬프트의 `requestedInfo` 이름과 똑같이 맞춘다.

### 3-3. 더 안전한 선택지: 입력 버튼 방식
개인정보 요구 장면에서 채팅창 대신 **"정보 보내기" 버튼**(가상 신분증 사진과 같은 방식)을 띄우면 원문이 아예 입력되지 않는다. 훈련의 핵심은 "보낼지 말지 결정하는 순간"이므로 교육 효과는 거의 같다. 다만 사용자가 채팅창에 직접 쳐 버리는 경우는 여전히 있으니, 가림은 그대로 둔다.

## 4. 서버가 채워야 하는 변수

| 변수 | 계산 방법 |
|---|---|
| `SCENARIO` | 시나리오 JSON (persona, channel, allowedOrganizations, scenes[request, requestedInfo, goal, tactic, expectedActions]) |
| `ESTABLISHED_FACTS` | 지금까지 LLM 이 낸 `newFacts` 누적 목록. 없으면 "(아직 없음)" |
| `CURRENT_SCENE`, `TOTAL_SCENES` | 상태값. 장면 이동은 LLM 의 `nextScene` 을 따르되 +1 넘게는 못 가게 |
| `SCENE_REQUEST_MADE` | 이 장면에서 `requestMade=true` 인 대사가 한 번이라도 있었는가 |
| `TRUST_COUNT` | 이 장면에서 move 가 `신뢰` 또는 (`답변후진행` & requestMade=false)였던 횟수 |
| `PUSH_COUNT` | 이 장면에서 move 가 `압박` 이었던 횟수. 장면이 바뀌면 0 |
| `USER_TURNS`, `MIN_TURNS`, `MAX_TURNS`, `TURNS_LEFT` | `TURNS_LEFT = MAX_TURNS - USER_TURNS` |
| `LAST_MOVE` | 직전 LLM 출력의 `move`. 첫 턴은 "(없음)" |
| `LINK_COUNT`, `APP_COUNT`, `ACCOUNT_COUNT` | 지금까지 보낸 personaMessage 속 소품 개수 |
| `SPEAKER_CHANGE_COUNT` | `speaker` 가 직전 화자와 달랐던 횟수 |
| `EVENT_LOG` | 서버가 기록한 사건 목록 (턴 번호 포함 권장: "3턴: 송금_누름"). 없으면 "(없음)" |
| `REQUESTS` | 허용 requestType 목록 |

`{{...}}` 가 치환되지 않은 채 LLM 에 넘어가지 않게, 보내기 전에 `"{{" in prompt` 를 검사해서 막는다.

## 5. 환각 방지 장치

환각은 프롬프트로 "하지 마"라고 하는 것만으로는 안 줄어든다. **LLM 이 기억하거나 세야 하는 것을 없애는 것**이 가장 효과적이다.

### 5-1. 프롬프트 쪽 (training_prompt.md)
- **사실의 출처를 네 곳으로 한정** (§5): 시나리오, 확정 설정, 대화 기록, 사건 기록
- **지어내도 되는 것 / 안 되는 것 목록**: 막연한 "환각 금지"보다 구체적인 목록이 훨씬 잘 지켜진다
- **모를 때 행동 지정** (§5-3): "얼버무리기"를 허용해서 사실을 지어내야 할 압박을 없앴다. 실제 사기범의 회피 화법과도 맞는다
- **판정 → 수 → 대사 순서의 JSON**: 판정과 move 를 먼저 쓰게 해서 대사가 결정표를 따르게 한다
- **출력 전 점검표** (§9)

### 5-2. 서버 쪽
- **`newFacts` → `ESTABLISHED_FACTS` 순환**: 한 번 말한 금액·시각·이름이 턴마다 바뀌는 문제를 막는다. 이것이 페르소나 일관성에 가장 크게 효과가 있다
- **상태값은 서버가 센다**: 소품 횟수, 압박 횟수, 턴 수, 사건 여부
- **`output_guard.validate()`**: 금지어, URL, 실제 번호처럼 보이는 숫자, 알 수 없는 대괄호, 소품 장면·한도·위치, 명분 없는 소품, 첫 메시지 소품, nextScene 범위
- **`apply_server_overrides()`**: 가림·사건이 있으면 risky 강제, 최소 턴 전 조기 종료 방지, 최대 턴 도달 시 종료

### 5-3. 모델 설정 권장
- temperature 0.6~0.8 (대사 다양성은 유지하면서 규칙 준수). JSON 이 자주 깨지면 0.5까지 낮춘다
- API 가 JSON 모드나 구조화 출력을 지원하면 켠다
- `max_tokens` 는 넉넉하게 (JSON 이 중간에 잘리면 전체가 실패한다)

### 5-4. 더 나아가는 선택지: 채점과 연기를 두 번의 호출로 분리
지금은 한 번의 호출로 채점과 연기를 같이 한다. 품질 문제가 계속되면 둘로 나눈다.
- **1차 호출 (채점자)**: temperature 0, 판정 JSON 만 출력
- **2차 호출 (배우)**: 판정 결과와 move 를 입력으로 받아 대사만 생성
- 장점: 판정이 대사 분위기에 끌려가지 않고, 배우 프롬프트가 짧아져 몰입감이 좋아진다
- 단점: 호출 2배 (비용·지연). 지금 구조는 섹션 단위로 나뉘어 있어서 §2(채점)와 §3~§6(연기)을 잘라 쓰면 된다

## 7. 이 저장소에 적용한 방식 (2026-11-23)

| 노트의 항목 | 적용한 곳 |
|---|---|
| 프롬프트 본문 | `app/prompts/training_turn.md` (첫 줄 `TASK: training` 유지). 사건 종류에 `공식경로_확인` 한 줄 추가 |
| 변수 채우기 (§4) | `training_turn._build_prompt` — 18개 자리를 모두 채우고, 빠진 자리가 있으면 LLM 을 부르지 않고 오류 |
| 상태값 (PUSH/TRUST/LAST_MOVE/ESTABLISHED_FACTS) | AI 가 `trainingState` 로 돌려주고, Spring 이 시나리오 진행 JSON 에 `currentScene` 과 함께 저장해 다음 턴에 돌려줌. 상태가 없으면(예전 백엔드) 대화 기록으로 짐작 |
| 소품·화자 횟수, EVENT_LOG | 매 턴 대화 기록에서 서버가 직접 셈. 버튼 사건은 대본에서 빼고 EVENT_LOG 로만 전달 |
| 가림 (`pii_masker.py`) | `app/guard/pii_masker.py`. 기존 `sensitive.py` 규칙 → `pii_masker` 순서로 두 번 가림. LLM 에는 `[가림:종류]`, 화면·DB 에는 기존처럼 `[종류]` |
| 출력 검사 (`output_guard.py`) | `app/guard/output_guard.py`. 서버가 고칠 수 있는 위반(소품 위치·한도, 장면 번호, 업체 표기 대괄호)은 다시 묻지 않고, 금지어·URL·번호·JSON 오류만 1번 재요청 → 그래도 안 되면 판정은 살리고 대사만 기본 대사 |
| 서버 덮어쓰기 | 가림·사건이 있으면 risky 강제, 최소 턴 전 조기 종료 방지, `realConcern` 이면 훈련을 멈추고 112·1332 안내 |
| 화자 변경 | `speaker` 필드를 `[화자: 이름] ` 머리말로 바꿔서 프론트로 보냄 (대화 전체 2번까지) |

통합하면서 `pii_masker.py` 에서 고친 점 (판정이 뒤집히는 과잉 가림 방지)
- "저는 ○○" 를 이름으로 보는 규칙 삭제 ("저는 싫어요"가 이름으로 가려져 위험 판정되던 문제)
- 이름은 성씨로 시작하고 흔한 말("정말", "이상해" 등)이 아닐 때만
- 거절·되묻기·의심이 담긴 답에는 문맥 가림(이름·주소·비밀번호 통째 가림)을 하지 않음
- 주소 문맥 가림은 숫자나 시·구 이름이 함께 있을 때만 ("어디로 보내요?" 오탐 방지)

예전 형식(`move` 가 없는 JSON, 테스트용 가짜 응답·mock LLM)이 오면 예전 보정 규칙(맴돌기 보정, 직접 입력 재요구 등)을 그대로 써요.
